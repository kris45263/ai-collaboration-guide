# 旧文档处理：任务提示词的修改前后

[用户材料与来源](input.md) · [生成条件](../generation.md) · [返回案例目录](../README.md)

两份正文都是实际子代理输出，未经人工改写。初稿未提供协作文档；修订稿参考了文档。这里展示变化，尚未评价哪版更好。

## 原始问题

我们发现手册里有一些内容已经不适用于当前版本，但还留在原来的位置，读者可能以为它们仍然准确。目前缺少统一的判断方式，也不清楚谁来决定一页内容是否过时，以及判定以后该怎么处理。

讨论里有人提出删除、留在原处加版本说明，或者移到归档区域。也有人反对删除：旧内容能解释系统为什么变成现在这样，培训资料还引用着这些页面；把它们移走也可能让人失去理解上下文。我想让 AI 帮忙梳理并处理这件事。

共同任务：根据上面的情况，整理一份可以直接发给另一个 AI Agent 的任务提示词，让它接手处理。只输出这份提示词。

修订使用的是去除个人表述之前的早期文档，案例未按当前发布版重跑。版本与生成过程见[生成说明](../generation.md)。

## 修改前

请接手梳理手册中的旧文档问题，建立可执行的判断和处理方式，并据此推进具体页面的整理。

背景：手册中有些内容已不适用于当前版本，却仍位于读者通常查找现行说明的位置。团队尚未统一如何判断内容过时、由谁作决定，以及判定以后如何处理。可选方案包括删除、原处保留并加版本说明、移入归档。旧内容同时可能具有历史解释价值，且已有培训资料引用，因此不能仅凭“旧”就认定应当删除。

目前没有提供待处理页面清单。请先查明可访问的文档范围、当前版本依据、文档维护规则和相关负责人。若无法获得这些资料，请明确列出缺失项，并先完成判断框架和待核实清单，不要虚构页面、负责人或已经完成的处理。

请按以下步骤开展：

1. 盘点候选页面。记录页面位置、适用版本、疑似过时的具体内容、支持判断的依据，以及页面的维护状态。区分“已经确认不适用”“部分内容需要更新”“只是较旧但仍准确”和“证据不足”，不要只按发布日期判断。
2. 核查用途与影响。检查页面是否仍被站内链接、培训资料或其他已知材料引用，是否包含现行文档没有说明的设计缘由、迁移信息或历史背景。明确核查范围，无法确认的外部引用应标为未知。
3. 提出统一处理规则。针对每种情况，说明何时更新为现行说明、何时在原处标注适用版本、何时归档、何时可以删除。说明各方案对读者理解、检索、引用连续性和维护成本的影响。允许拆分页面：将仍有效的说明纳入现行手册，将历史内容保留为独立记录。
4. 明确决策责任。查找现有规则中的内容维护人、版本或技术审核人及最终决策人。若没有规定，提出一套简洁的责任与复核流程，作为待确认建议；不要自行宣称某人拥有审批权。
5. 为具体页面提出处理建议。每页应包含问题、证据、处理方式、理由、引用影响、所需审核和具体修改草案。归档页面需醒目标明适用版本和归档原因，并链接到现行替代说明；移动页面时应考虑保留原链接或设置重定向；删除前应确认没有需要保留的独有信息，并准备可恢复记录。

先交付盘点结果、判断规则和逐页处理方案，供相关负责人审核。没有明确的编辑授权时，不直接修改或删除页面。获得授权后，按确认的范围实施，记录每页的修改与去向，并验证原链接、重定向、现行说明和已知培训引用是否仍能正常使用。对无法验证或尚有争议的页面，保留待办状态并写明下一步需要谁提供什么信息。

最终报告应让未参与讨论的人也能理解：发现了什么问题、依据是什么、采用了什么规则、哪些修改已完成、哪些仍待决策，以及后续如何定期复核，避免归档内容再次被误认为现行说明。

材料中的 WordPress 讨论只提供历史问题背景，不能据此推断当前项目或 WordPress 现在的文档状态。请以实际可核查的项目资料支持具体判断。

## 参考协作文档修订后

请帮我们梳理并处理手册中的旧文档问题。

我们发现，有些内容已经不适用于当前版本，却还留在原来的位置，读者可能以为它们仍然准确。目前还没有统一的判断方式，也不清楚由谁决定一页内容是否过时，以及判定以后该怎么处理。

讨论中有人提出删除、留在原处加版本说明，或者移到归档区域；也有人反对删除，因为旧内容能解释系统为什么变成现在这样，培训资料还引用着这些页面，移走后也可能使人失去理解上下文。这些是需要比较的意见，尚未决定采用哪一种。我们希望既能让读者清楚哪些说明适用于当前版本，也能妥善处理仍有历史价值或被引用的内容。

请先了解实际可访问的手册、当前版本依据和已有维护规则，判断问题具体出现在哪里，再提出处理建议。调查方法由你选择；如果发现问题不只是内容过时，还涉及版本说明、页面入口或其他因素，请说明它们如何导致读者误解，以及是否需要调整本次处理范围。

目前没有提供待处理页面清单或项目入口。若工作环境中能找到明确属于本项目的资料，可以先开展核查；若不能，请说明需要补充的入口或材料，并先整理可供讨论的判断方式。不要把缺少资料时提出的框架写成已经完成的页面调查，也不要用假设页面充当实际发现。

梳理时，需要把以下几件事分清楚：

- 内容较旧与内容已经不适用，是不同的判断。具体页面可能仍然准确、部分需要更新、只适用于旧版本，或暂时缺少判断依据。请用可核查的版本信息和具体内容支持判断。
- 是否适合继续作为现行说明，与是否值得保留，是两个问题。核查旧内容是否包含仍需保留的背景、设计缘由或迁移信息，以及已知的链接和培训引用；说明实际查到了什么，哪些影响还不清楚。
- 删除、原处加版本说明和归档各自解决什么问题，又可能带来什么问题。结合实际页面比较读者辨认现行说明、理解上下文和继续使用引用的需要；必要时也可以建议更新或拆分页面，不必把所有页面套进同一种处理方式。

请据此提出简洁、可执行的判断和处理规则，并查明已有的决策责任。没有现成规定时，说明哪些判断需要内容维护者或熟悉版本的人核实、哪些分歧需要团队决定，再提出责任安排的建议，不要把建议写成已经生效的制度。

对于能实际核查的页面，给出足以支持决定的具体建议：哪里存在误导或不适用，依据是什么，建议如何处理，以及对有价值的信息和已知引用有什么影响。可以用修改草案帮助我们判断建议是否合适。已有明确规则和授权的事项可以继续推进；仍取决于团队选择、责任确认或未知影响的操作，先把需要决定的事情说清楚，再根据结果处理。若建议迁移或删除，需要说明原链接和仍需保留的信息将如何安排。

向我们说明工作时，请让没有参加原讨论的人也能理解关键发现及其意义。把具体问题、判断依据和建议的理由联系起来，清楚区分已经核实的情况、尚未确认的影响、建议和实际完成的修改，并指出哪些未解问题会影响下一步决定。表达形式按实际内容选择，不需要复述完整操作日志。

背景材料来自 WordPress Documentation 团队 2020 年的公开讨论《What to do with old/obsolete documentation》：https://make.wordpress.org/docs/2020/12/17/what-to-do-with-old-obsolete-documentation/ 。这里提供的是项目整理的中文概述，并非参与者的逐字原话；它只用于说明历史讨论中的问题和分歧，不能据此判断本项目或 WordPress 当前的文档状态。具体页面的判断应以本次可核查的项目资料为依据。
