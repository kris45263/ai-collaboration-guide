# AI 协作参考

我经常先和 AI 讨论一个尚未想清楚的问题，再让它把讨论整理成给另一个 Agent 的任务提示词。

整理过程中，原本只是猜测的原因，可能被写成确定前提；暂时想到的方案，可能被写成必须执行的步骤；为了保险加上的要求，也可能让任务说明越来越繁重。

这份文档从个人协作经验中整理了一些方法：保留原始含义，把目标和必要责任说清楚，让假设保持可检验，让还没决定的事情保留判断空间，并说明怎样的结果才真正回应了原来的问题。

另一个常见场景是：Agent 完成工作后，汇报里写着“修复竞态”“检查通过”，你却仍不清楚原来发生了什么、它具体改了哪里。文档的“把实际工作讲清楚”部分用于帮助 Agent 把这些联系讲清楚，让读者理解调查发现、修改过程和实际结果。这份文档也可用于整理原始表达和交接上下文。

## 怎样使用

### 整理或修订给 Agent 的任务提示词

生成 Agent 任务提示词时，可以这样开始：

1. 将[协作文档](个人AI协作文档.md)的内容或文件，以及自己的原始表达、讨论记录等材料，提供给负责整理的 AI。
2. 说明希望它产出一份给另一个 Agent 的任务提示词。
3. 检查整理结果是否保留了自己的意思，再将提示词和执行所需材料交给接手的 Agent。

可直接使用的请求：

> 请参考这份协作文档，根据下面的表达，整理一份可以交给另一个 Agent 的任务提示词。

如果已经有一份提示词，请同时提供原始材料、已有稿件和协作文档：

> 请参考这份协作文档，结合原始材料重新审视并修订这份提示词，使其更准确地传达我的意图、目标和协作需要。

原始材料能帮助 AI 判断哪些要求来自你，哪些可能是此前整理时新增的。接手的 Agent 是否还需要协作文档，取决于后续任务；可以先从上述整理流程开始使用。

### 让 Agent 把工作说明讲清楚

可以在交给 Agent 的任务中附上协作文档，请它参考“把实际工作讲清楚”说明工作；也可以在看不懂汇报时，直接让完成工作的 Agent 重新解释：

> 请参考协作文档的“把实际工作讲清楚”部分，重新说明这次工作。我希望理解原来发生了什么、修改怎样起作用，以及你实际检查到了什么。请结合具体过程，把这些事情之间的联系讲清楚。

例如，“修复了项目切换时的异步竞态”可以展开为：先打开项目 A，再切到 B；B 的文件先返回，随后返回的 A 文件又覆盖了页面。再说明修改后怎样处理晚到的 A 文件，读者就能理解问题与修复之间的关系。完整表达示例见[同一项工作的两种说明](个人AI协作文档.md#explanation-example)。

如果交给另一个 AI 改写，应同时提供它需要的工作记录或相关材料。仅凭一句“测试通过”，无法知道实际检查了哪些情况；缺失的事实需要从记录中查找或向原 Agent 询问。

### 在讨论中澄清问题、修正理解

当你还在比较想法，或已经纠正过 AI 的理解，却发现后面的建议仍沿用旧前提时，可以提供相关讨论和纠正内容，请 AI 参考[讨论、检查与修正判断](个人AI协作文档.md#reason)。

> 请结合这次纠正重新检查前面的讨论，更新受影响的判断和建议，保留仍然成立的部分。

### 整理讨论与交接上下文

需要把长讨论交给新会话或另一个 Agent 时，提供原始记录，并说明接手者要继续什么工作。文档的[理解与整理原始材料](个人AI协作文档.md#understand)和[形成任务说明与交接](个人AI协作文档.md#handoff)可帮助保留关键背景、已有决定和仍待判断的问题，处理修改历史与最终产物的区别。

## 怎样查找相关内容

| 当前需要 | 文档入口 |
| --- | --- |
| 理解、重述或压缩原始表达 | [1. 理解与整理原始材料](个人AI协作文档.md#understand) |
| 澄清问题、检查方案、安排验证或处理纠正 | [2. 讨论、检查与修正判断](个人AI协作文档.md#reason) |
| 生成提示词、交接任务或整理最终产物 | [3. 形成任务说明与交接](个人AI协作文档.md#handoff) |
| 理解 Agent 实际做了什么、怎样得到结果 | [4. 把实际工作讲清楚](个人AI协作文档.md#explain) |

如果已经遇到具体问题，例如“猜测被写成事实”“新 Agent 缺少背景”或“汇报都是标签”，可以从 [D：按问题查找与调用](个人AI协作文档.md#lookup) 直接定位条目。各部分可以组合使用，不是一套固定执行顺序。

本文中的“用户”指当前任务的使用者，不预设其个人经历或偏好。当前明确要求优先于一般建议；无需把整份文档转成每次任务的检查清单。

首批公开案例选择了三种任务：

| --- | --- | --- |
| 为长对话交接编写任务提示词 | 压缩后丢失进展，考虑每轮更新交接文件 | [查看](examples/01-handoff/comparison.md) |
| 为协作方式调整编写任务提示词 | 赶交付时质量不满意，完整技能流程又增加开销 | [查看](examples/02-workflow/comparison.md) |
| 为旧文档处理编写任务提示词 | 内容不再适用，但历史解释、引用和读者需求仍然存在 | [查看](examples/03-documentation/comparison.md) |

案例输入根据公开社区讨论作中文整理，来源和项目添加的任务设定均在各案例中注明。每份初稿由一个独立 AI 子代理生成，再由另一个子代理参考本文的早期版本修订。两版文字原样保留。案例生成后，正文去除了个人原话与特定经历，并按用途重组了章节。案例没有按当前发布版重跑。

这些案例展示本项目中实际发生的文字修改，供读者检查变化是否有意义。它们不是原帖作者使用本文档的记录，也尚未经过效果评估。修订同时增加了一次重新审视的机会，不能仅凭两版差异判断文档的独立作用。具体生成方式见[案例说明](examples/README.md)。

## 来源与后续更新

文档起于个人协作经验，也参考了技术写作、上下文管理和解释质量等外部资料；相关来源和适用边界保留在正文中。对模型行为的描述应结合版本与实际使用经验理解。

后续会根据具体使用情况修订。反馈如果能包含原始材料、当时希望 AI 做什么、实际输出，以及哪里偏离了你的意思，会更容易讨论。
